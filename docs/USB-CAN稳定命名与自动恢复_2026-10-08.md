# USB-CAN 稳定命名与自动恢复（2026-10-08）

## 业务接口定义

| 项目 | 当前定义 |
| --- | --- |
| 开发板 | LoongOS / 2K0300，实机 SSH `root@192.168.3.112` |
| 应用 | PatrolSystem v1.24.0，本次不替换应用二进制 |
| USB 适配器 | 单个 XCAN-USB，PCAN 兼容，正常 VID/PID `0c72:000c` |
| 异常下载模式 | `314b:0106 / APM32 DFU ISP Mode`；须退出 BOOT/下载模式再重新上电 |
| 业务接口 | `can2`，`link.type=can`，500000 bit/s，经典 CAN |
| 固定命名 | `/etc/modprobe.d/pcan-can2.conf`：`options pcan assign=pcan32:can2` |
| 身份核实 | PCAN 8.14 的 `/proc/pcan` 中唯一的 `usb` 接口；此驱动的 netdev 为 virtual，不能依赖 netdev 的 USB 父路径 |
| bus-off 恢复 | `restart-ms=100`；仅启用恢复，不故意制造总线错误 |
| 接口恢复检查 | `usb-can2-recover.timer`，启动后 15 秒起检查，间隔 5 秒，调度精度 1 秒 |
| 应用重连 | 接口重新出现、ifindex 改变或配置被修复后，重启正在运行的 `patrol.service`，重建 SocketCAN 与相关线程 |

`can0/can1/can2` 是接口名，不等于板载 CAN 控制器或引脚身份。本次 USB 适配器重新插入后曾被驱动自动命名为 `can0`；不能沿用历史文档中的编号映射判断硬件。

当前仅定义一个 PCAN USB 适配器。检测到多个 USB CAN 通道，或目标 `can2` 已被其他设备占用时，恢复脚本会报错并拒绝改动。板载 CAN 不由本脚本启用。增加第二个适配器前需重新定义设备映射。

UART 是手动选择的备用传输，不是 CAN 失败后的自动回退。本次不改变 F4 固件、GPIO、屏幕引脚、内核、设备树和网络设置。

## 本次故障与修复

最初适配器枚举为 DFU，`pcan` 已加载但 `/proc/pcan` 为 0 interfaces，应用所需的 `can2` 不存在。重新插拔退出 DFU 后，驱动创建 `can0`，而应用和启动服务仍使用 `can2`，造成第二层配置不匹配。

新增恢复脚本会加载驱动，核实唯一 PCAN USB 接口，必要时将其改名为 `can2`，配置 500 kbps、正常收发模式及 `restart-ms=100`。已经正确配置的接口不会被反复 down/up；相同 ifindex 的健康检查不会反复重启应用。

原启动服务仍负责业务启动前初始化，失败时保留视频/网络服务的启动机会。定时恢复任务独立运行，因此适配器晚插入或服务首次启动失败后仍会重试。设备缺失时会撤销接口就绪记录，并停止仍标记 active 的 CAN 初始化服务；接口恢复后重新启动该服务。DFU/缺失/冲突/恢复状态输出明确诊断，重复的相同状态不重复输出脚本诊断文本。

接口恢复会使现有应用重启，上位机 TCP 连接需重新建立。已被用户停止的应用不会被恢复脚本主动启动。接口健康只表示驱动和链路配置就绪；F4 业务健康仍以遥测计数、心跳和错误计数为准。

## 安装与后续发版

Git 仓库：`ML08081/Long`，本次基于远端最新的 `feat/Qt` 分支。相关文件已放入 `deploy/scripts`、`deploy/systemd`、`deploy/modprobe`，并接入 `scripts/make_package.sh` 和 `deploy/install.sh`，后续正式部署包会包含本次修复。

新安装默认配置为 `link.type=can`、`can_if=can2`。已有 `/etc/patrol/config.json` 仍由主安装脚本保留；只有该配置选择 CAN 时，主安装脚本才安装 CAN 支持。保留的 UART 配置不会被强制切换。

可以在仓库中独立安装：

```sh
sudo sh deploy/scripts/install_usb_can_recovery.sh
```

也可在生成的正式部署包中执行 `sh scripts/install_usb_can_recovery.sh`。`--install-only` 安装、校验和启用开机项，不强制初始化接口或重启应用；原本已运行的恢复定时器会在更新后继续运行。新安装在正常启动 `patrol.service` 时会通过依赖启动恢复定时器。

安装前自动备份被替换文件、缺失文件清单与原开机启用状态至 `/root/can-recovery-backup-YYYYMMDD-HHMMSS/`。适配 LoongOS 的 BusyBox `flock`，不使用其不支持的 `-w`；系统没有 `systemd-analyze` 时，通过 daemon-reload 后的 LoadState 校验和实际启动检查服务加载。

实机首次备份为 `/root/can-recovery-backup-20261008-123535/`。该备份早于任何配置替换，回退本次完整修改应使用它，而非后续安装兼容性修正时产生的备份。

本次板端只更新原运行配置中的说明字段，保留全部实际参数。不要用 Windows 根目录的旧屏幕配置覆盖板上配置。

## 检查命令

```sh
cat /proc/pcan
cat /sys/module/pcan/parameters/assign
/sbin/ip -details -statistics link show can2
systemctl is-active usb-can2.service usb-can2-recover.timer patrol.service
cat /run/loong-usb-can-can2.status
journalctl -u usb-can2.service -u usb-can2-recover.service -n 40 --no-pager
journalctl -u patrol.service -n 40 --no-pager
timeout 8 /usr/bin/candump can2
```

预期：`/proc/pcan` 显示 `usb can2`，驱动参数为 `pcan32:can2`，CAN 为 `ERROR-ACTIVE`、500000 bit/s、restart-ms 100；收到 `0x181/0x281/0x381/0x701`，应用日志 RX 计数增长且 `hb=ok`，错误计数不增长。

服务 active 不能单独证明 F4 通信正常。旧应用二进制仍有“检查 can0”的历史错误提示，应以实际配置 `can2` 和上述恢复脚本诊断为准。

## 实机验证

| 检查 | 结果 |
| --- | --- |
| USB 恢复后的原始链路 | 500 kbps 监听 8 秒，158 帧，错误/丢帧 0 |
| 应用初始化 | `CanManager: can2 就绪`、下位机链路正常 |
| 应用收发 | RX 遥测递增、`hb=ok`；CAN TX 计数递增，err/boff/tec/rec 均为 0 |
| 接口被手动置 DOWN | 定时任务约 3 秒后恢复接口并重启应用 |
| 健康状态幂等性 | 连续两次执行恢复检查，应用 PID 不变 |
| 板载接口重名 | 指定已被板载设备占用的 can1，脚本拒绝操作，板载接口保持 DOWN |
| USB 驱动断连/重连模拟 | 仅解绑 PCAN USB 接口，缺失状态被检测；重新绑定后约 4 秒恢复 can2 和应用 |
| 固定命名持久配置 | 卸载/重载 pcan 后，驱动直接生成 can2，assign=pcan32:can2，无需等待改名 |
| 开机项 | usb-can2.service 和 usb-can2-recover.timer 均 enabled |
| 正式包目录结构 | 独立恢复包按 scripts/systemd/modprobe 布局安装通过，--install-only 保持应用 PID 与运行中的定时器 |
| 最终稳定采样 | RX 6372 / TX 6452 帧，错误/丢帧/bus-off 均为 0，应用最新心跳 hb=ok |

断连测试期间有意中断链路，曾累计 2 个 RX dropped；重新加载驱动后计数重置，最终验收以新接口的稳定采样为准。未执行整板重启或长时间电机满载测试，也未注入运动测试命令。

复查时另发现摄像头 `/dev/video0` 已不存在，应用因此显示 DEGRADED；CAN 心跳及遥测仍正常，该问题需要单独检查摄像头的 USB 连接。

## 回退

在开发板执行，使用本次首次备份：

```sh
systemctl stop usb-can2-recover.timer usb-can2-recover.service
systemctl disable usb-can2-recover.timer
systemctl stop patrol.service usb-can2.service
# 下面三个文件在首次备份的 absent.list 中，均为本次新增。
rm -f /etc/systemd/system/usb-can2-recover.service
rm -f /etc/systemd/system/usb-can2-recover.timer
rm -f /etc/modprobe.d/pcan-can2.conf
tar -C / -xzf /root/can-recovery-backup-20261008-123535/files.tar.gz
rm -f /run/loong-usb-can-can2.state /run/loong-usb-can-can2.status
systemctl daemon-reload
systemctl reset-failed usb-can2.service
systemctl start patrol.service
```

回退恢复原文件和服务行为，不保证原故障条件下 CAN 可以通信。驱动当前已加载的 assign 参数会保留到下次重载/重启；回退配置后如需立即恢复原驱动命名，先停应用并关闭 USB-CAN，再重载 pcan。其他日期或其他安装状态的回退，应按对应备份的 existing.list、absent.list 和启用状态执行，不能照搬本次新增文件清单。
