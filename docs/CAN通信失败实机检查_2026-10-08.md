# CAN 通信失败实机检查（2026-10-08）

> 本文记录故障定位过程。后续修复已完成部署与验证，最终接口定义、安装、验收和回退见《USB-CAN稳定命名与自动恢复_2026-10-08》。

## 结论

已通过免密 SSH 登录 `root@192.168.3.112`（主机名 `LoongOS`，内核 `4.19.190+`）。本次通信失败的直接原因是 USB-CAN 适配器处于 DFU 固件下载模式，未生成业务配置要求的 SocketCAN 接口 `can2`。

本次只读检查，没有更改开发板配置、重启服务、刷写固件或发送运动命令。

## 实机证据

- USB 路径 `/sys/bus/usb/devices/3-1`：VID/PID `314b:0106`，产品名 `APM32 DFU ISP Mode`。
- 正常工作时应枚举为 `0c72:000c / XCAN-USB`，见既有《CAN链路STOPPED问题诊断与修复方案》第 3 节方案 B。
- `lsmod` 显示 `pcan` 已加载；`/proc/pcan` 显示 `0 interfaces`。驱动已存在，但没有匹配的正常工作模式适配器。
- `/sbin/ip -br link` 中没有 `can2`，仅有板载 `can1`（DOWN）。接口 DOWN 时显示 STOPPED，不能据此判断本次板载驱动是否故障。
- `usb-can2.service` 状态为 `failed`，启动脚本等待 `can2` 约 10 秒后退出，退出码 1。
- `patrol.service` 在运行，但日志明确显示：`找不到 CAN 接口 can2(No such device)`、`CAN 接口 can2 打开失败`、`下位机链路: 未接入 (CAN can2)`。

故障链：适配器进入 DFU → PCAN 无匹配设备 → can2 不存在 → CAN 启动服务失败 → 应用无法打开 CAN → F4 通信不可用。

本次尚不能确认触发 DFU 的具体原因，也尚不能判断恢复正常 USB 枚举后的 F4 接线、终端电阻和总线通信情况。

## 恢复步骤

1. 将 USB-CAN 适配器 USB 线拔下后重新插入，避免按住 BOOT/下载键；如果有 BOOT 跳帽或模式开关，恢复正常运行位置。若适配器有其他供电路径，需要完整断电再上电。
2. SSH 登录开发板，先确认 USB VID/PID 恢复为 `0c72:000c`，并出现 `can2`；如果仍为 `314b:0106`，继续检查 BOOT 状态与适配器固件，重启业务服务无法解决该状态。
3. 确认正常枚举后执行：

```sh
systemctl restart usb-can2.service
/sbin/ip -details -statistics link show can2
systemctl restart patrol.service
timeout 8 /usr/bin/candump can2
```

预期：`can2` 为 `ERROR-ACTIVE`、bitrate 为 `500000`，持续收到 F4 的 `0x181 / 0x281 / 0x381 / 0x701` 等帧。最后检查应用日志中遥测计数持续增长和心跳恢复，再判定端到端通信恢复。

如果恢复后的接口名称不是 `can2`，先核对设备对应关系，再调整服务与应用配置，不能仅按接口编号切换到板载 CAN。

## 附带发现

- CAN 启动脚本只在启动时等待约 10 秒，没有热插拔自动恢复逻辑。
- 应用通过 `Wants=usb-can2.service` 依赖 CAN 服务，CAN 服务失败后应用仍会启动，因此“应用运行中”不等于 CAN 通信正常。
- 应用部分错误提示仍写“检查 can0”，但实际配置为 `can2`，排查时应以实际接口配置为准。

## 用户重新插拔后的复查

再次登录 `192.168.3.112` 后确认：

- USB 设备已恢复 `0c72:000c / XCAN-USB`，内核识别为 `PCAN-USB fw v8.4`。
- 驱动生成的实际接口为 **`can0`**，不是业务配置中的 `can2`。
- `/proc/pcan` 明确显示 `32 usb can0`。此时这个 `can0` 是 USB-CAN，不能套用历史文档中“can0 为占用屏幕引脚的板载控制器”的映射；接口名需要结合驱动和设备身份判断。
- `usb-can2.service` 仍失败，应用仍无法打开 `can2`。因此退出 DFU 后，当前剩余阻塞点为接口名称与服务、应用配置不匹配。

为了核实物理链路，在确认 USB VID/PID、驱动绑定及 `/proc/pcan` 对应关系后，临时将 USB `can0` 设置为 `500000` 并启用，监听 8 秒，没有发送应用层 CAN 帧或运动命令：

- 收到 `0x181 / 0x281 / 0x381 / 0x481 / 0x701` 等 F4 上行帧。
- RX 共 `158` 帧、`1237` 字节，errors 和 dropped 均为 `0`。
- 状态 `ERROR-ACTIVE`，`txerr=0`、`rxerr=0`、bus-off 为 `0`。
- TX packets 为 `0`，本次未验证下行命令与应答。

监听结束后已将 USB `can0` 恢复为 DOWN，未修改服务或应用配置、未重启应用。以上证明本次采样期间 F4 上行 CAN 链路可用，但应用通信尚未恢复。

后续修复应统一 USB-CAN 接口命名、启动服务与应用配置，建议按 USB 设备身份稳定命名为 `can2`，并补齐热插拔恢复。不能直接启用未经身份核实的同名板载接口。
