# 上电掉线、供电与持续鸣响排查

日期：2026-10-23。本记录对应此前启动修复之后的新现场。基线源码为 `044cf0238b3d3d1b0afcb2336b1c757e1e79f045`。

## 当前结论与限制

尚不能确定整机掉电的电气根因，也未解决模块实际持续鸣响。用户确认目前由电脑供电、蜂鸣器仍持续叫；电脑USB具体接入哪条电源轨、蜂鸣器VCC电压、触发跳帽状态，以及随后是否人为拔线，都尚待确认。

现场采样时龙芯和F4均在运行，不能将当时的数据缺失直接解释为整个程序堵塞。程序堵塞本身不能作为电源电压下跌的证据；供电是否带载下降，需要测量实际电源轨。

## 已取得的事实

- 龙芯可SSH访问，启动ID `3ed14ad8-ea8b-481f-9c0d-442ca863373b`，应用重启数0；空闲内存充足。热像解算帧从27持续增长至178，温度约31～33°C，说明采样时系统及F4热像任务仍运行。
- CAN始终没有有效F4遥测。F4命令接收计数为0，出现大量CAN错误、bus-off及恢复操作；一次读数为错误9776、bus-off9776、恢复3560，软件故障计数达到8。
- 原代码会将CAN恢复错误累计至看门狗阈值8，即使其他任务仍存活，也可能停止喂狗。这具有触发重复复位的条件，但本次没有完整复位日志，不能据此断言每次掉线都由看门狗造成。
- F4运行计时曾出现回退，尚需区分用户主动断电、供电复位和看门狗复位。旧固件已清除RCC原始复位标志，不能事后补读当次原因。
- ST-Link采样目标电压约3.25V。这只是当时MCU电压，不是整机5V电源轨测量，也不能排除上电瞬间跌落。
- 蜂鸣器请求模式为0、当前鸣响状态为0；PB8配置为输出且输入/输出均为高电平。同时用户确认模块持续鸣响，因此尚需检查模块触发极性/跳帽、实际IN对模块GND电压、共地与供电，不能继续仅靠交换软件高低电平来猜测。
- TIM1四路比较值均为0，没有检测到驱动电机PWM输出。转向与云台当时处于中位保持。
- 原程序每次启动仍会执行转向极限自检和云台全行程扫描。这会增加启动负载，重复复位时还会重复动作，但目前没有电流/电压测量证明其为掉电唯一根因。
- 后续约16:50，ST-Link从电脑USB层消失，龙芯也无法访问；尚不清楚是用户断开还是供电/USB链路中断，不能将这一现象直接归因于固件。

## 已完成的软件修改（未烧录）

1. 默认关闭转向上电自检与云台上电全行程扫描，保持中位；台架自检保留显式编译开关。
2. CAN恢复限频至最多每秒一次，异常状态不继续向发送邮箱排队；不再因外部CAN故障累计触发整机复位，保留任务超时及非CAN故障的看门狗检测。原有命令心跳停车逻辑保持。
3. 在清除RCC标志之前保存 `g_boot_reset_flags`，日志输出原始复位位；避免仅凭BOR标志就把普通电源复位标成已证实的供电不足。寄存器语义依据 [ST RM0090](https://www.st.com/resource/en/reference_manual/dm00031020-stm32f405-and-stm32f407-advanced-armbased-32bit-microcontrollers-stmicroelectronics.pdf)。

完整编译通过：FLASH111672字节、RAM54568字节。CAN故障隔离、蜂鸣器、F4运行控制、运动策略、编码器、循迹、避障意图及I2C恢复八组回归通过。CAN回归运行实际CAN恢复/发送与看门狗代码，验证持续外部故障不使健康任务复位、恢复限频、真实任务停滞和其他故障仍停止喂狗。

## 下一步硬件核验

先明确电脑USB具体给龙芯、F4、载板还是外设供电，是否同时接有其他电源。若使用9月14日冻结的载板，应按现有电源域文档核对J1的5V、J2的3.3V及公共地，不能直接套用旧版VIN供电说明，也不能在电源隔离未确认时并联外部电源和USB供电。

先确认控制板供电稳定，再逐支路检查舵机、外设和CAN收发器供电；记录上电前后5V/3.3V及模块输入电压。蜂鸣器需核对实际模块型号/触发设置，并比较PB8及模块IN相对同一GND的电压。供电与调试连接恢复后，再刷入待验证固件，观察原始复位标志、连续运行时间及实际声音；当前不进行电机行驶测试。

证据目录：`power-check-20261023`。`f4-initial-read.log`含寄存器现场，`local-validation.json`及各验证日志含本地回归结果。`f4-observation.log/json`的后续记录为“调试器已消失，未取得寄存器”，不能当作成功的连续运行监测。
