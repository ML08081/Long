## 二、根因诊断

### 问题 1【致命 · 根本原因】`main.c` 是执行器硬件自检测试程序，从不启动 RTOS

修复前的 `Core/Src/main.c` 并不是迁移后的产品代码，而是一段遗留的**执行器自检测试**：

- 只初始化了 `GPIO / DMA / TIM1 / TIM2 / USART6` 五项外设；
- **缺失** `USART2`(龙芯) / `USART3`(蓝牙) / `I2C1`(OLED) / `TIM3`/`TIM4`(编码器) 的初始化；
- **缺失** `OLED_Init / Encoder_Init / HC_Init / Servo2_Init` 等业务模块初始化；
- `main()` 进入一个 `while(1)` 的舵机/电机循环测试，**永不退出**；
- 从未调用 `osKernelInitialize()` / `MX_FREERTOS_Init()` / `osKernelStart()`——**FreeRTOS 调度器根本没有启动**。

**连锁后果**：由于工程链接选项启用了 `-Wl,--gc-sections`（裁剪无引用代码段），而 `main()` 不引用 `MX_FREERTOS_Init`，于是 `freertos.c` 中的全部任务（`MotionControlTask` 蓝牙遥控、`ScanTask` 超声波/OLED）连同整个 FreeRTOS 内核、OLED、编码器、超声波模块全部成为"无人引用"的死代码，被链接器整体丢弃。

这正是"能编译通过却无法运行任何产品功能"的假象来源，也解释了 RAM 仅 3.7KB 的异常现象（32KB 的 FreeRTOS 堆被裁掉了）。

### 问题 2【链接错误 · 修复问题 1 后暴露】`UART_Log` 未定义

`Core/Inc/main.h` 声明了 `void UART_Log(...)` 并定义了 `LOG()` 宏，`freertos.c` 中大量使用 `LOG()`。但测试版 `main.c` 只定义了 `__io_putchar`，**没有定义 `UART_Log`**。

修复前因为 `freertos.c` 被整体裁剪、没人调用 `UART_Log`，所以侥幸没有报错；一旦接回 RTOS，`UART_Log` 立即成为未定义符号（undefined reference），链接失败。

### 问题 3【运行期卡死 · 隐藏炸弹】`TIM2_IRQHandler` 缺失

F4 的超声波采用**非阻塞状态机 + TIM2_CH2 输入捕获中断**方案（相对 F1 的升级）。`Core/HC/hc.c` 的 `HC_Init()` 会：

- 使能 TIM2 通道 2 捕获中断 `CC2IE`；
- 使能 TIM2 更新（溢出）中断 `UIE`；
- 使能 `TIM2_IRQn` 的 NVIC。

而 TIM2 配置为 1µs tick、ARR=19999，**每 ~20ms 必然溢出一次**。但 `Core/Src/stm32f4xx_it.c` 中**没有 `TIM2_IRQHandler`**，于是溢出中断会跳转到启动文件中弱定义的 `Default_Handler`（死循环）——**只要调用了 `HC_Init()`，系统约 20ms 后即卡死**。

修复前因 `main.c` 从不调用 `HC_Init()` 而未暴露；接回完整初始化后，这是必然触发的致命问题。

### 问题 4【非缺陷 · 按用户要求保留】IWDG 未配置

`freertos.c` 的两个任务中存在 `IWDG->KR = 0xAAAA;`（喂狗）写操作，但 F4 工程：

- `stm32f4xx_hal_conf.h` 中 `HAL_IWDG_MODULE_ENABLED` 处于**注释关闭**状态；
- `Drivers/.../Src/stm32f4xx_hal_iwdg.c` 驱动源文件**不存在**；
- 没有 `iwdg.c / iwdg.h`。

由于用户明确说明"有部分在 F4 中没有进行配置，不要做大改动"，**IWDG 属于有意未配置的部分**。看门狗未启动时，向 `IWDG->KR` 写值是**无害的空操作**，不影响系统运行。因此本次**不引入 IWDG**（引入它需要打开 HAL 模块、补齐缺失的驱动源、改链接配置，属于"大改动"）。如未来需要看门狗保护，见"第六节"。

## 三、修复内容（逐文件）

### 1. `Core/Src/main.c` —— 重写初始化与启动流程（核心修复）

移除遗留的执行器自检测试，恢复为标准的"外设初始化 → 业务模块上电 → 启动 RTOS"流程，对齐 F1 的 `main.c` 结构，并适配 F4 的引脚与时钟：

- **保留**：F4 的 HSI 时钟配置（HSI→PLL→168MHz）、`EarlyError_*` 紧急诊断、`__io_putchar`、`vAssertCalled`、`HAL_TIM_PeriodElapsedCallback`、`Error_Handler`、`assert_failed`；
- **补齐外设初始化**：`MX_GPIO/DMA/TIM1/TIM2/TIM3/TIM4/I2C1/USART2/USART3/USART6`；
- **补齐业务上电**：TIM1 四通道 PWM 启动、`DRV8701_Enable`、`Servo_Init`、`OLED_Init`、`Encoder_Init`、`HC_Init`、`Servo2_Init`，以及启动横幅日志；
- **接回调度器**：`osKernelInitialize()` → `MX_FREERTOS_Init()` → `osKernelStart()`；
- **新增 `UART_Log()` 定义**（输出到 `USART6`/`huart6`），修复问题 2。USART6 是独立调试通道，不占用 USART3 蓝牙数据帧通道。

### 2. `Core/Src/stm32f4xx_it.c` —— 新增 `TIM2_IRQHandler`

在文件末尾 `USER CODE BEGIN 1` 区域新增 ISR，修复问题 3：

```c
void TIM2_IRQHandler(void)
{
  /* 更新中断（溢出）→ 累加 32 位微秒计数高位 */
  if ((TIM2->DIER & TIM_DIER_UIE) && (TIM2->SR & TIM_SR_UIF))
  {
    TIM2->SR = ~TIM_SR_UIF;     /* 清除更新标志 */
    HC_OnTimerOverflow();
  }
  /* 通道 2 捕获中断 → ECHO 边沿处理 */
  if ((TIM2->DIER & TIM_DIER_CC2IE) && (TIM2->SR & TIM_SR_CC2IF))
  {
    HC_TIM2_IRQHandler();       /* 内部清 CC2IF */
  }
}
```

- `it.c` 已 `#include "hc.h"` / `"tim.h"`，`HC_OnTimerOverflow()`、`HC_TIM2_IRQHandler()` 接口在 `hc.h` 中已声明，无需额外改动；
- 该 ISR 同时服务"溢出计数"（供 `HC_GetUs()` 拼出 32 位微秒时间戳）与"ECHO 边沿捕获"两类中断；
- 放在 `USER CODE` 区域内，CubeMX 重新生成时不会被覆盖。

> 其余文件（`usart.c` 的 USART3 RX 状态机与回调、`DMA1_Stream3_IRQHandler`、`USART3_IRQHandler`、`TIM6_DAC_IRQHandler`、各业务模块）经核查均已就绪，无需改动。

## 八、转向舵机不动 / 按键无效 —— 定时器分频修正（2026-06-29 第三次迭代）

### 现象
上板日志显示：启动序列、云台扫描、转向舵机自检（`SELF-CHECK 1/3→DONE`）流程都跑完，但**转向舵机几乎不动**、**按键控制电机前进/后退无效**，且 `[SCAN] dist=0 cm` 恒为 0、自检结束 `pulse=1527`（非 1500）。

### 根因：F1→F4 定时器分频未按新时钟重算（迁移遗留 bug）
F1（STM32F103）主频 72MHz，TIM 时钟 72MHz，`PSC=71` 恰好得到 1MHz（1 tick = 1µs）。F4 工程**直接照抄了 F1 的 `PSC=71`**，但 F4 时钟树不同：

| 定时器 | F4 时钟 | PSC=71 实际 | 应为 | 已修正 PSC | 影响 |
|--------|---------|-------------|------|-----------|------|
| TIM1 电机 PWM | 168MHz (APB2×1) | 2.33MHz → 2.33kHz | 1kHz | **167** | PWM 频率偏高（电机仍转，影响小）|
| TIM2 舵机+HC | 84MHz (APB1×2) | 1.167MHz | 1MHz | **83** | **舵机脉宽全部缩水 ~14%** |
| TIM3 编码器1 | 外部时钟 | 脉冲 ÷72 | ÷1 | **0** | 编码器计数慢 72 倍 |
| TIM4 编码器2 | 外部时钟 | ÷1（本就 0） | ÷1 | 0 | 正常 |

**为什么舵机像"不动"**：`servo.h` 的脉宽常量是 µs 单位（中位 1500、左 1711、右 1300），代码假设 1 tick=1µs。但 TIM2 实际 1.167MHz 时，`CCR=1500` 只输出 **1285µs**、左右极限变成 1466/1114µs——舵机被压在一个偏离中心的 ±175µs 窄带内微动，且 PWM 周期变成 17.1ms(58Hz)。修正 `PSC=83` 后恢复 1µs/tick：中位 1500µs、行程 1300~1711µs、50Hz，舵机正常满行程摆动。HC-SR04 的 `HC_GetUs()` 同样依赖 1µs/tick，一并修正测距精度。

### 修复（`Core/Src/tim.c`）
- `htim1.Init.Prescaler`: 71 → **167**
- `htim2.Init.Prescaler`: 71 → **83**
- `htim3.Init.Prescaler`: 71 → **0**

### 按键控电机：逻辑正确，加了诊断
代码路径核查无误：本地模式（`active=0/LOC`）下读 PA11/PA12（上拉，按下=0），置 `current_speed=±500`，经 `Motor1/2_Set()` 输出。日志中整段 `spd=0` 且无 `[BTN]`，说明这段时间按键**始终读到未按下**。为区分"接线问题"还是"逻辑问题"，已在 3 秒心跳日志追加按键**原始电平**：

```
DBG: ... LOC BTN(PA11=1 PA12=1 idle=1,pressed=0)
```

**排查指引**：
1. 按住前进键看该行 → 若 `PA11` 由 `1` 变 `0`：接线/逻辑都正常，电机应转并打印 `[BTN] FWD ... FORWARD`。若电机仍不转 → 检查 DRV8701 外部使能开关（`DRV8701_Enable()` 当前为空函数，依赖板上硬件开关）。
2. 按键时 `PA11/PA12` **始终为 1 不变** → 按键未接到 PA11/PA12，或按键另一端没接 GND（应为"按下接地"的 active-low 接法）。
3. 空闲时就读到 `0` → 该脚被外部下拉或接线接反。

> 编译验证：0 错误，RAM 40192 B (30.66%)，FLASH 55560 B (10.60%)。

## 九、按键极性 + 左满舵 —— 上板复测修正（2026-06-29 第四次迭代）

第三次迭代加入的"按键原始电平"诊断行直接定位了根因。上板日志稳定显示：

```
DBG: ... LOC BTN(PA11=0 PA12=0 idle=1,pressed=0)
```

### 问题 1：按键极性反了（致使按键完全无效）
**空闲未按键时 PA11/PA12 都读到 0**（尽管固件配了内部上拉）。说明硬件是**高电平有效**接法：空闲被外部下拉到 0、按下接到 VCC=1。而原固件按**低电平有效**（空闲 1、按下 0）写判断，条件 `btn==0 && other==1` 永远不成立 → 按键永远触发不了，`spd` 恒为 0。

**修复**：
- `Core/Src/gpio.c`：PA11/PA12 由 `GPIO_PULLUP` 改为 `GPIO_PULLDOWN`（空闲稳定为 0；ENC1_B/PA7 编码器方向仍保持上拉，已拆分单独配置）。

### 问题 2：转向舵机左满舵不够
PSC 修正后舵机已能正常摆动，但左极限（+90°）行程偏小。
- `Core/Servo/servo.h`：`SERVO_PULSE_LEFT_MAX` 由 `1711` → **`1800`**（µs）。映射约 2.28µs/°，即每 +23µs≈+10°。如仍不够/或过冲撞限位，微调此一个宏即可（右极限 `SERVO_PULSE_RIGHT_MIN=1300` 不变）。
