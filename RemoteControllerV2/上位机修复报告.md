## 二、数据帧核查（结论：一致，无需改）

F4 端 `protocol.c/h`（权威）与上位机 `protocol.cpp` 逐字段对比：

| 字节 | 含义 | F4 (`Protocol_PackFrame`) | 上位机 (`packCommand`) | 一致 |
|------|------|---------------------------|------------------------|------|
| [0] | 帧头 | 0xAA | 0xAA | ✅ |
| [1..2] | speed (大端, int16) | high,low | high,low | ✅ |
| [3..4] | steering (大端, int16) | high,low | high,low | ✅ |
| [5] | mode | 命令帧 bit7=0 | 0/1/2 (bit7=0) | ✅ |
| [6] | 校验 | byte0~5 异或(XOR) | byte0~5 异或(XOR) | ✅ |

- **命令/遥测区分**：F4 用 mode 的 bit7 区分——命令帧 bit7=0，遥测帧 bit7=1，且 F4 会**主动拒绝 bit7=1 的帧**（防 BT 回环）。上位机命令 mode 取值 0/1/2，bit7 恒为 0 → 不会被 F4 拒绝。✅
- 次要提示（不影响遥控）：上位机 `config.h` 的 mode 语义（STOP/JOYSTICK/BUTTON）与 F4 的 mode 语义（MANUAL/AUTO/OBSTACLE/CRUISE）不同，但 F4 蓝牙控制只依据 speed/steering 驱动电机与舵机，不依据 mode 值，故无影响。

## 三、连通性根因与修复（核心）

### 根因：BLE 收发特征（TX/RX）角色搞反
标准 Nordic UART Service：
- **6e400002 = RX 特征**，属性 **Write / WriteWithoutResponse**：中心端(PC)**写入**它 → 模块从自身 UART TX 把数据发往 **STM32 的 RX(PB11)**。
- **6e400003 = TX 特征**，属性 **Notify**：模块**通知**中心端 → PC 用来**接收**遥测。

原 `bledevicemanager.cpp` 按 UUID 标签赋值（`onServiceStateChanged`）：
```
m_txChar(用于订阅通知) = 6e400002   // 实际是只能“写”的特征 ❌
m_rxChar(用于写命令)   = 6e400003   // 实际是只能“通知”的特征 ❌
```
而 `sendData()` 是往 **m_rxChar** 写命令——也就是写到了 6e400003（Notify-only 特征）。**对只支持通知的特征写入会被丢弃，命令永远发不出去** → F4 端 `USART3 got 0 bytes this second`（与实测日志完全吻合）。

### 修复：改为“按属性识别”，不再按 UUID 标签
特征角色由 GATT 属性唯一确定，按属性识别可彻底消除命名歧义，且对标准 NUS、JDY 变体、HM-10/CC2541(FFE0 单特征双向) 均通用：

```cpp
// m_rxChar = 写命令的目标：必须含 Write / WriteWithoutResponse  (NUS 6e400002)
if (ch.properties() & (Write | WriteWithoutResponse))  m_rxChar = ch;
// m_txChar = 订阅通知的来源：必须含 Notify / Indicate       (NUS 6e400003)
if (ch.properties() & (Notify | Indicate))             m_txChar = ch;
```
修复后：`sendData()` 写入的是真正的写特征(6e400002) → 模块转发 → 到达 STM32 PB11；通知订阅(CCCD)落在 6e400003 → 正常接收遥测。

### 附带修复：移除 AT 指令对透传链路的污染
- **30s 保活定时器**原本向透传特征写 `AT\r\n`。修复角色后它会真的把 `41 54 0D 0A` 注入 STM32 数据流（之前日志中出现过的 4 字节就是它）。BLE 连接由协议栈维持，无需应用层保活——**已清空该定时器的写操作**。
- **连接时**原本先发 `AT\r\n` 再发测试帧。连接态下模块透传、不解析 AT，AT 只会变成下游垃圾——**已移除连接时的 AT**，保留 `AA 00 00 00 00 00 AA`（一帧合法 STOP）作为**连通性自检**：连上后 F4 端应能立即解析到 1 个有效帧。

### 改动文件
| 文件 | 改动 |
|------|------|
| `bledevicemanager.cpp` | ① 特征识别改为按属性（修复 TX/RX 反向）② 保活不再写 AT ③ 连接自检改为发 STOP 帧、移除 AT |

> 其余文件（`protocol.cpp`、`mainwindow.cpp` 发送路径、`wifimanager`、`bluetoothmanager`）核查无误，未改动。

## 六、第二轮修复（2026-06-29，基于双端实测日志）

实测发现该模块**不是 NUS，而是 HM-10/CC2541 风格的 `0xFFE0` 服务**，含两个特征：
| 特征 | 属性 | 角色 |
|------|------|------|
| `0xFFE1` | Write + WriteNoRsp + **Notify** | ✅ 透传数据管道（写它→出模块 UART→STM32；UART 回来的数据以通知返回）|
| `0xFFE2` | Write + WriteNoRsp | ❌ 非数据特征（写它不转发 UART）|

### 问题 1：写特征被 FFE2 误覆盖（命令发不到 STM32）
第一轮“按属性选第一个可写特征”的循环里，FFE2 在 FFE1 之后出现，把写目标 `m_rxChar` 从 FFE1 覆盖成了 FFE2 → 命令写到 FFE2，模块不转发 → STM32 仍收不到控制帧（只收到模块自身的 `+DISC:SUCCESS` 状态文本，证明模块 UART→STM32 接线本身是好的）。

**修复**（`bledevicemanager.cpp`）：写特征**优先选“可写且可通知”的透传管道**（FFE1），仅在不存在这种合并式特征时才退而用纯写特征（NUS 拆分式的 6e400002）。FFE2 这类纯写特征不再误覆盖。对 NUS（6e400002 写 / 6e400003 通知）与 HM-10（FFE1 双向）均正确。

### 问题 2：连接每 ~37s 断开（不稳定）
第一轮把保活完全移除后，空闲时上位机完全不发数据，BLE 链路被模块/系统按空闲断开。
**修复**（`mainwindow.cpp` 发送心跳）：运动时每 3 tick(~50ms) 重发当前帧，**空闲时每 15 tick(~250ms) 也重发**一次。既保持链路活跃，又因 250ms < F4 的 510ms 心跳超时，使 F4 持续显示“蓝牙在线”。FFE2 误写也可能曾诱发模块断开，修复问题 1 后应一并缓解。
> 注：写到正确的 FFE1 后，若仍偶有断连，多为模块/系统 BLE 行为；上位机已具备自动重连（最多 3 次），重连后控制即恢复。

### 改动文件（第二轮）
| 文件 | 改动 |
|------|------|
| `bledevicemanager.cpp` | 写特征优先选 Write+Notify 透传管道(FFE1)，避免被 FFE2 覆盖 |
| `mainwindow.cpp` | 增加空闲心跳(250ms 重发)，维持 BLE 链路与 F4 在线 |

编译：qmake+mingw32-make 通过，0 错误，已重建并覆盖部署 `RemoteController_v2.exe`。

## 七、第三轮（关键判定）：上位机已正确，故障在“模块未透传 BLE→UART”

第二轮后实测双端日志显示：
- **上位机侧**：已正确把合法帧写入 **FFE1**（`aa 00 00 fc 18 02 4c`、`aa 02 58 00 00 02 f2`=速度600、`aa fd a8 ..`=速度-600 …），WriteWithoutResponse，无任何写错误。**上位机功能正确，无需再改逻辑。**
- **F4 侧**：全程 `BTDBG RX +0B total=0`，USART3 一个字节都没收到。

### 判定（基于硬证据）
- 此前 F4 曾收到干净可读的 `+DISC:SUCCESS`（115200 正确解码）→ **证明“模块 UART_TX → STM32 PB11”接线与波特率都正确**。
- 现在 PC 向 FFE1 写了上百帧合法数据，F4 却 0 字节 → **模块把自己的状态 URC 发给了 STM32，却没有把 BLE 收到的负载数据从 UART_TX 转发出来**。
- 结论：**这不是上位机软件 bug，而是模块没有进入“透传/直通(transparent)”数据模式**（会打印 `+DISC` URC 是 AT/命令模式的典型特征），或所连设备并非车上那只模块。

### 新增诊断（本轮上位机改动）
为区分“GATT 写是否到达模块” vs “模块是否转发到 UART”，连接时的自检帧改用**带响应写(WriteWithResponse)**，并新增两类日志：
- `✅ 写入已确认(模块已收到 GATT 写, N 字节)` ← 模块在 GATT 层确实收下了写；
- `⚠️ 服务错误(写入可能失败): code=N` ← GATT 写失败。

**据此判读：**
| 上位机日志 | F4 是否收到字节 | 结论 |
|------------|----------------|------|
| ✅ 写入已确认 | 否(total 仍 0) | **模块未透传**：进透传模式 / 换正确特征 / 确认是车上模块 |
| ⚠️ 服务错误 | 否 | GATT 写被拒：特征/连接问题 |
| ✅ 写入已确认 | 是(ok>0) | 链路打通 ✅ |

### 隔离测试（强烈建议，按此定位）
1. **确认连对了设备**：把车上的蓝牙模块断电，在上位机重新扫描——列表里 `<YYY>` 应随之消失。若不消失，说明你连的是另一只设备（扫到 3 个设备）。
2. **手机 BLE 助手直连测试**：用手机 nRF Connect / BLE 调试助手连同一模块，向 FFE1 写入 16 进制 `AA 00 00 00 00 00 AA`，看 F4 调试串口 `ok` 是否 +1。
   - F4 `ok+1` → 模块透传正常，问题在 PC 端环境（少见，因本机日志已确认写成功）。
   - F4 仍 0 → 模块未透传，与上位机无关。
3. **USB-UART 旁路测试**：把模块 UART_TX/RX 接到一个 USB-TTL（115200）开串口助手；从上位机连 BLE 并发帧，若串口助手能看到 `AA ...` 字节 → 模块透传 OK，问题在模块↔STM32 接线；若看不到 → 模块未透传。

### 模块配置方向（若确认未透传）
该模块会打印 `+DISC:SUCCESS` 等 URC，属 AT 风格固件。需用 USB-UART 在**未连接(命令模式)**下用 AT 指令将其设为**透传/直通**数据模式（不同型号指令不同，常见如设角色=从机、模式=透传、波特率=115200、可关 URC）。设好后 BLE 写入才会从 UART 吐出。
> 如告知确切模块型号（JDY-31 / BT04-A / DX-BT24 / HM-10 等）及其 AT 手册，可在上位机连接后自动下发对应的“进透传”初始化序列。
